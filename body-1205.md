## Question

What is `PickerSheet`'s keyboard and screen-reader contract on web?

Ruling 7 removes typed date entry, and #1185 settled the sheet's structure — so this is now answerable. The two elements being deleted, `<input type="date">` and `<input type="time">`, provided the entire web keyboard and assistive-technology contract **for free**: arrow-key date stepping, type-ahead, a labelled combobox role, and locale-aware announcements. Nothing replaces them automatically.

Decide:

- **Focus on open.** Where does focus land when the sheet opens — the card, the selected day, `Done`? And where does it return on close? `PressShieldModal` does not manage focus; react-native-web's `ModalFocusTrap` force-refocuses whatever was focused when the modal opened, which is the #1034 behaviour the #1054 gate exists to bound.
- **Escape.** `onRequestClose` is wired on all three copies today. Under ruling 6, Escape **discards**. Is that the same path as the backdrop tap, and is discarding-on-Escape discoverable enough to be the only way out, given #1160's app-wide "visible way out" rule?
- **Tab order inside the sheet.** The backdrop is deliberately `tabIndex: -1` on web (sighted keyboard users have Escape; touch-exploration screen readers keep a labelled close). With a `Clear` / `Done` footer (#1184), what is the tab cycle, and does the calendar grid participate or is it one stop?
- **Is the calendar grid reachable and announced at all?** `react-native-ui-datepicker` renders `Pressable` days under react-native-web. Whether those become focusable elements with usable roles/labels is unverified — and ☠️ `getByRole` in RNTL never matches a plain `View`, so jest cannot answer this. It needs a rendered probe.
- **Arrow-key navigation.** If the grid is a single stop, is there arrow-key day movement, or is the calendar mouse/touch-only on web? Ruling 7 already concedes a speed regression; this decides whether it is also an accessibility regression, and the spec must state which.
- **What the trigger announces** when unset ("No date set", #1184) versus set.

⚠️ Constrained by #1185: the sheet is `PressShieldModal` → sibling backdrop → card → children → footer, and drafting is internal, so nothing is announced as committed until `Done`.

Use `/grilling` and `/domain-modeling`. A rendered probe is likely needed — see the `rendered-contrast-probe` and `rnw-onlayout-mount-observation` patterns.

## ⚠️ Amended by [What replaces the web time input, at each of its five call sites](https://github.com/Selftend/selftend/issues/1191)

Two of the premises above have changed, and this ticket gains a surface.

**The time half of the premise is now false.** The framing *"the two elements being deleted, `<input type="date">` and `<input type="time">`, provided the entire web keyboard and assistive-technology contract for free — nothing replaces them automatically"* holds for the date, but not the time. #1191 ruled that ☠️ the library's web time control has **no accessibility at all** — `wheel-web.js` is a bare `PanResponder` drag surface with no `tabIndex`, no role, no `aria-*`, and not one accessibility prop anywhere in the library's `time-picker/` directory — so the replacement is an in-app control of **two numeric `HH : MM` fields** (plus an AM/PM `SegmentedControl` in 12-hour locales), which is keyboard-native by construction.

**That control's own contract is decided here**, not on #1191:

- **Accessible names for three sub-controls.** Hour, minute and AM/PM each need a name, and today the five call sites pass a single `accessibilityLabel` (e.g. `"Sleep reminder time"`). Is the sub-name generic (`"Hour"`) with a group relationship carrying the context, or composed (`"Sleep reminder time, hour"`)? ⚠️ New i18n keys in both locales either way — and see #1173's WCAG 2.5.3 finding on what an accessible name may not drop.
- **Group semantics.** Does the trio form a labelled group, and what role — `group`, or nothing at all?
- **Tab cycle.** Three stops (or two, in `bg`), auto-advance hour → minute after two digits. ☠️ Auto-advance moves focus without the user asking, which is disorienting for switch and screen-reader users; decide whether it is suppressed under assistive technology or unconditional.
- **Announcing the revert.** Invalid input commits nothing and the field visibly snaps back on blur (#981's contract, kept). Sighted users see it; is it announced?

**The sheet's own contract is unchanged for `date` and `range`.** For `datetime` on web the tab cycle now runs **calendar → `HH` → `MM` → (AM/PM) → footer** in one view, because #1191 removed the library's view switcher and put the time row beneath the calendar.

**`TimeField` never opens a sheet on web at all** — it renders the control inline at all five sites — so nothing about focus-on-open, Escape, or the backdrop applies to time entry. Those questions remain live for the date modes only.
