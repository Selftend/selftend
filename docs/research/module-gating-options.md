# Runtime feature toggles with the approved stack

Research for [#2450](https://github.com/Selftend/selftend/issues/2450) under map [#2445](https://github.com/Selftend/selftend/issues/2445) (the modules' production status). Resolved AFK on 2026-09-15.

**Every pricing and policy claim below was checked on 2026-09-15** against the official page linked beside it. Re-check before acting on a number; Expo's plan limits and Apple's agreement text both move.

This document **does not choose a mechanism**. It feeds the mechanism ticket on #2445 with facts. Where a statement is inference rather than a sourced fact it is marked _assumption_.

## The question

With the approved stack only - Expo built-ins, Supabase, TanStack Query - what can toggle a feature (here: a module's presence on the production surfaces) at runtime on iOS, Android and web, and what does each option cost?

## What the repo already has (verified on `origin/dev` at `1c97653d`, 2026-09-15)

- **No `expo-updates`.** `package.json` lists `expo` ^57 (line 73) and `expo-in-app-updates` ^0.12.0 (line 84 - the Play Core "update available" popup from #388, a store-update prompt, not an OTA channel). `package-lock.json:8816` carries `expo-updates-interface` transitively; that is the interface package a development client links against, not the updates library. `app.config.ts` has no `updates` key and no `runtimeVersion`; its `extra` holds only `eas.projectId` (`app.config.ts:367-371`). `eas.json` names an EAS `environment` per build profile (`development` / `preview` / `production`) and no `channel` on any profile.
- **Three places state "no OTA channel" as a load-bearing premise**: `test/check-in-route-compat.test.tsx:18-22`, `supabase/functions/_shared/web-reminders.ts:231-233` and `app/(app)/tools/mood-tracker/index.tsx:8-10`. All three reason that a client change is a store release with an unbounded tail of never-updating users. Adopting EAS Update would not make those guards wrong - the tail of users who never take an update still exists - but the comments would need rewording so a future reader does not "fix" them.
- **Build-time env is the only gate pattern.** `src/lib/env.ts:3-42` reads `process.env.EXPO_PUBLIC_*` with `??` fallbacks; the "empty string drops the surface" rule is documented at `env.ts:5-9`. `test/web-deploy-public-env.test.ts` fails when a reader whose fallback ends in `""` is not forwarded by `.github/workflows/web-deploy.yml`'s `env:` block.
- **Web gets its env from GitHub Environments.** `web-deploy.yml:30` selects the environment (`production` by default, `staging` when `staging.yml` calls it), `web-deploy.yml:38-61` forwards `vars.EXPO_PUBLIC_*` into the export, `web-deploy.yml:125-134` runs `npm run export:web` and writes `dist/version.json`. Production deploys on a published Release, staging on every push to `dev` (`docs/deployment.md:60-61`).
- **Native gets its env from EAS environments at build time.** `docs/internal-testing.md:25` (the `preview` and `production` profiles use matching EAS environments) and `:159-171` ("Rebuild the AAB after changing any of those values. Existing Play builds keep the environment values that were baked in at build time"). Native builds compile on GitHub runners with `eas build --local` and upload with `eas submit` (`docs/releasing.md:168`); Android goes to the Play production track as `completed` (`docs/releasing.md:74-76`), iOS needs a manual App Store Connect promotion (`docs/releasing.md:156-160`).
- **A launch-time remote read already exists.** `src/lib/update-availability.ts:57-66` resolves `/version.json` (same-origin on web, `EXPO_PUBLIC_PUBLIC_APP_URL` on native) and `:74-89` fetches it, treating every failure as "no answer". `public/_headers:40-41` serves it `Cache-Control: no-cache`; `src/lib/use-update-availability.ts:55` throttles the check to once per 6 h. Only the web build acts on it today (`docs/deployment.md:191`).
- **The app already talks to Expo's servers from user devices**: native push tokens are minted through Expo's push service using `extra.eas.projectId` (`src/lib/push-token.ts:19-21`). Expo is therefore an existing processor, not a new party - but an update check would be a new per-launch flow from every install, which is the thing the ticket asks to flag.
- **TanStack Query**: the query cache is persisted to AsyncStorage on native only, for 24 h, and never on web (`src/lib/query-client.ts:16-31`); queries keep TanStack's default `networkMode: "online"` and mutations use `"always"` (`query-client.ts:87-96`). The root layout holds the native splash only until fonts load (`app/_layout.tsx:46`, `:93-101`); nothing waits on a network read before first render.
- **`user_preferences.enabled_modules`** exists, defaults to `['cbt']` (`supabase/migrations/20260415_initial.sql:22`) and gates nothing (`src/features/modules/types.ts:302`). It is a per-user preference column, not an operator flag; it is listed here only so nobody mistakes it for one.
- **Two Expo-adjacent third parties already ship in the client**: Sentry (`@sentry/react-native`, `app.config.ts:342-361`) and Expo push. Neither is a flag service and neither should become one.

## Answers to the ticket's four questions

### 1. EAS Update / `expo-updates`

**Built-in?** Yes as a library: `expo-updates` is an Expo SDK module installed with `npx expo install expo-updates` (<https://docs.expo.dev/eas-update/getting-started/>, checked 2026-09-15), which falls under `docs/stack.md:108` "Expo modules for platform capabilities". The dependency-policy questions still apply to the _service_: EAS Update is "a cloud service that serves updates for projects using the expo-updates library" (<https://docs.expo.dev/eas-update/introduction/>). It is a new hosted dependency (Expo's update CDN), a new CI step, and a new per-install network flow - the architecture rule in `AGENTS.md` makes that a control-tower inventory entry.

**Does the repo carry it?** No - see "What the repo already has". `expo-updates-interface` in the lockfile is not the library.

**Free plan, checked 2026-09-15 at <https://expo.dev/pricing>:**

- Free: "Send updates to 1K MAUs", 100 GiB update bandwidth, no overage (the Free plan has no overage pricing - the limit is a cap).
- Starter ($19/month, per `docs/costs.md:55`): 3K MAUs, 100 GiB then $0.10/GiB; MAU overage graduated from $0.005/MAU.
- Production: 50K MAUs, 1 TiB. Enterprise: 1M+ MAUs, 40 TiB.
- MAU definition, verbatim: "A user who downloads one or more updates is counted as a single MAU. Users who do not download updates during the billing cycle are not included in the MAU count."
- Builds: Free includes 15 Android and 15 iOS cloud builds a month, which is irrelevant here - the pipeline builds with `eas build --local` on GitHub runners (`docs/releasing.md:168`).

_Assumption_: at the map's stated non-owner population (a handful of people across three modules; `auth.users` counts are not on the public issue) the 1K MAU cap is not a near-term constraint. It becomes one only if the whole user base takes an update in one month, which is exactly what a module withdrawal update would do.

**What adoption changes about the release process** (`docs/deployment.md`, `docs/internal-testing.md`, `docs/releasing.md`):

- A one-time `eas update:configure`, which writes `updates.url` and `runtimeVersion` into the app config and a `channel` onto the `preview` and `production` build profiles, and touches native files (AndroidManifest / strings.xml / Expo.plist) - so **a new store build on both platforms precedes the first update** (<https://docs.expo.dev/eas-update/getting-started/>).
- A runtime-version policy to choose and honour. "Whenever we make changes to our native code that change our app's JS-native interface, we'll need to update the runtime version" (<https://docs.expo.dev/eas-update/how-it-works/>). The `appVersion` policy ties the runtime version to `package.json`'s version, which release-please bumps on every release - with that policy every release is a new runtime and an update only reaches installs of the _same_ version. The `fingerprint` policy hashes native code instead. Either way it is a new invariant to record in `docs/releasing.md`.
- A new job in `release.yml` (`eas update --channel production --environment production`) after the migration gate, using the existing `EXPO_TOKEN` secret, plus the decision of _when_ an update ships versus a store build: today every release is a store build; with updates, a JS-only release could skip the stores, which changes the skew rules in `docs/releasing.md:112-132`.
- Every runtime-version build keeps its own update line. `preview` builds (testers) and `production` builds are on different channels, which is how a gated module could be "on" for testers and "off" for production - the "what dev-only means" open question on the map.
- `docs/internal-testing.md:25` and `:159-171` (env is baked at build) stay true for `EXPO_PUBLIC_*` values, since an update inlines the values of the environment it was published with (`--environment`, <https://docs.expo.dev/eas-update/environment-variables/>).

**Store-review posture, checked 2026-09-15:**

- Apple App Store Review Guideline **2.5.2**, verbatim: "Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app, including other apps." (<https://developer.apple.com/app-store/review/guidelines/>). Guideline **2.3.1** in the same document: "Don't include any hidden, dormant, or undocumented features in your app; your app's functionality should be clear to end users and App Review. All new features, functionality, and product changes must be described with specificity in the Notes for Review section of App Store Connect".
- Apple Developer Program License Agreement **§ 3.3.2** (the clause the ticket names), verbatim from a public copy filed with the SEC (Exhibit 10.36, <https://www.sec.gov/Archives/edgar/data/1581760/000119312522172365/d328928dex1036.htm>): "Except as set forth in the next paragraph, an Application may not download or install executable code. Interpreted code may be downloaded to an Application but only so long as such code: (a) does not change the primary purpose of the Application by providing features or functionality that are inconsistent with the intended and advertised purpose of the Application as submitted to the App Store, (b) does not create a store or storefront for other code or applications, and (c) does not bypass signing, sandbox, or other security features of the OS." Apple's 2025-10-08 developer news item says the current agreement moved and "Updated requirements related to interpreted code" under **§ 3.3.1(B)** (<https://developer.apple.com/news/?id=fnkpd51y>); the live text is behind a developer sign-in and was not read for this note. _Assumption_: the interpreted-code carve-out survives in substance - Expo's own guidance is written on that basis - but the exact 2025 wording is unverified here and the owner's Apple account can read it.
- Expo's own rule: "One of the rules of EAS Update is that you need to follow the rules of the platforms and app stores you are building for" and updates must follow store guidelines "including the content of the updates and how you use them" (<https://docs.expo.dev/eas-update/introduction/>).
- Google Play **Device and Network Abuse** policy, verbatim (<https://support.google.com/googleplay/android-developer/answer/9888379>): "An app distributed via Google Play may not modify, replace, or update itself using any method other than Google Play's update mechanism. Likewise, an app may not download executable code (such as dex, JAR, .so files) from a source other than Google Play. This restriction does not apply to code that runs in a virtual machine or an interpreter where either provides indirect access to Android APIs (such as JavaScript in a webview or browser)." A JS bundle is interpreted code under that exception.
- What this means for a **withdrawal**: removing a module's entry point through an update takes features _away_; it does not add ones inconsistent with the listing. The exposure is the other direction - the Play listing bullets the CBT and ACT tools (`store/play-listing.md:52-53`) and Apple's promo text names CBT thought records (map #2445), so an update that hides those while the listing still advertises them is the 2.3.1 "marketing your app in a misleading way" shape, whichever mechanism does the hiding. That is a store-copy amendment on the map's docs bill, not a property of EAS Update.

**Bundle.** `expo-updates` adds a native module and its assets to both binaries (size not measured here - _assumption_: single-digit MB, unverified). It is disabled in development builds and Expo Go (`Updates.isEnabled` false; <https://docs.expo.dev/versions/latest/sdk/updates/>), so local development is unchanged.

### 2. A Supabase-backed remote flag

**RLS shape for world-readable, owner-writable.** Supabase's own rule: once RLS is enabled, "no data is accessible through the API when using a publishable key, until you create policies", and each operation needs its own policy (<https://supabase.com/docs/guides/database/postgres/row-level-security>, checked 2026-09-15). So:

```sql
create table public.feature_flags (
  key text primary key,
  enabled boolean not null default false,
  updated_at timestamptz not null default now()
);
alter table public.feature_flags enable row level security;
create policy "feature_flags_read_all" on public.feature_flags
  for select to anon, authenticated using (true);
-- no insert/update/delete policy: the API cannot write; the owner writes
-- through migrations or the SQL editor (service role bypasses RLS).
```

"Owner-writable" then means _written by the operator through a migration or the dashboard_, not by any app user - matching the repo's rule that schema and RLS live in `supabase/migrations` (`docs/stack.md:126`). The publishable key "only reaches what Row Level Security allows" (<https://supabase.com/docs/guides/api/api-keys>), which is exactly the one `select`. Guests are anonymous Supabase users in this app, so `authenticated` covers them; `anon` covers the pre-session moment.

**Offline and guest behaviour with TanStack Query.** Default `networkMode: "online"` (`src/lib/query-client.ts:87-96` sets no override for queries): a query mounting for the first time offline sits at `status: 'pending'`, `fetchStatus: 'paused'` (<https://tanstack.com/query/latest/docs/framework/react/guides/network-mode>). On native, `PersistQueryClientProvider` restores the last successful value for up to 24 h (`query-client.ts:16-27`, `src/providers/app-providers.tsx:34-81`), so an install that has read the flag once keeps that value offline; web has no persister (`query-client.ts:19-24`), so an offline web arrival has no flag at all and must fall back to the built-in default. The persisted cache is cleared on sign-out (`query-client.ts:33-36`), which also drops the cached flag. Guest and registered users are indistinguishable to the read.

**Expo-blessed "read before first render"?** No such pattern for remote config. What Expo blesses is holding the splash: `SplashScreen.preventAutoHideAsync()` then `hideAsync()` once the app's own readiness condition is met - which is what `app/_layout.tsx:46` and `:93-101` already do for fonts on native. Two honest shapes follow:

- **Default-first**: render the compiled default (module shown or hidden), re-render when the read lands. Simple; risks a visible flip on Home on the first launch after a change.
- **Splash-gated**: add the flag read to the `ready` condition on native with a timeout, so a slow network cannot hold the splash indefinitely (`updates.fallbackToCacheTimeout` is Expo's equivalent knob for A). Web paints immediately by design (`_layout.tsx:86-89`) and would stay default-first.

_Assumption_: for a withdrawal the safer compiled default is "hidden", so a person offline or on a slow link never sees a module the operator has turned off; the trade is that a person on a flaky first launch may briefly not see one that is on.

### 3. Build-time env only

Expo's environment-variables guide (<https://docs.expo.dev/guides/environment-variables/>, checked 2026-09-15): the `EXPO_PUBLIC_` reference "will be replaced with [the value] in your app bundle" and "These variables will be visible in plain-text in your compiled application" - inlined at bundling, not read at runtime. The repo records the same fact for web at `docs/deployment.md:103` ("baked into the JavaScript bundle during export") and `:111`, and for native at `docs/internal-testing.md:170`.

Cost of a value change per platform:

- **Web**: set the variable on the GitHub Environment, forward it in `web-deploy.yml:38-61` (the test pins this for `?? ""` readers), redeploy - a Release for production (`docs/deployment.md:60`) or a push to `dev` for staging (`:61`). No review queue.
- **Android**: set it on the EAS `production` environment, cut a release (`docs/releasing.md:23-36`), Play review, then the auto-update tail; no rollback, only a higher `versionCode` (`docs/releasing.md:96`).
- **iOS**: the same plus the manual App Store Connect promotion (`docs/releasing.md:156-160`), and iOS users stay on the old client until that promotion happens (`docs/releasing.md:42`).

So build-time env can gate a module _differently per environment_ (staging on, production off; `preview` on, `production` off) but cannot flip production native without a store release - the map's "a native store build carries whatever flag value it was built with" premise is confirmed.

### 4. Anything else Expo ships

- **`expo-constants` `extra`** - "Values are accessible via `Constants.expoConfig.extra`" (<https://docs.expo.dev/versions/latest/config/app/>). Determined when the app config is evaluated: at export on web, at build on native, and inside each update if EAS Update is adopted. Not runtime-changeable on its own.
- **EAS environment variables per build profile** (`eas.json` `environment`, <https://docs.expo.dev/eas/environment-variables/>) - three named sets (`development`, `preview`, `production`), applied at build (and at `eas update --environment`). A per-profile difference, not a runtime one.
- **EAS Update rollouts** - "roll out a change to a portion of your users" by percentage per update or per branch (<https://docs.expo.dev/eas-update/rollouts/>); a bundle split, requires A. The docs do not say how a client is assigned to a percentage. _Assumption_ (from the client-ID page's sampling statement): assignment derives from the EAS client ID.
- **`updates.requestHeaders` / `Updates.setExtraParamAsync`** - segment which update a client receives; requires A.
- **Nothing else.** Expo has no remote-config product. Sentry (already present) has feature-flag _evaluation tracking_ integrations, which is the analytics direction the ticket forbids - not considered.

## Constraints, restated against the findings

- **No new third-party dependency**: options B, C, D and E add no package. Option A adds an Expo SDK module (policy-approved category) plus Expo's update service (new hosted dependency: the three questions are answered above - problem: flip native without a store release; why not approved stack: B and E flip the same surfaces with no new service; cost: an Expo-side per-install request on every launch, a runtime-version discipline, and a new release step).
- **No tracking or analytics SDK rides in**: none of the options brings one. Option A's per-launch request is what Expo bills "Update MAU" from and what its dashboard groups by installation; Expo states the request carries no unique device identifier, only a random per-install token. It is still a new data flow to a processor and needs the privacy review and a privacy-policy line. Options B and E create no new party.
- **Date and link on every pricing/policy claim**: in the table and § 1.

## The trade in one paragraph

Only three things flip production native without a store release: **EAS Update (A)** - heavy adoption, a new native build first, a per-install request to Expo on every launch, store-review posture to manage, and useless for every install already in the field; **a Supabase flag (B)** and **a static flags file on the web origin (E)** - both read at launch by the _existing_ code paths and infrastructure, both no new party, both needing the same client-side gate on every surface the map inventories, and both taking effect only on installs that can reach the network. **Build-time env (C/D)** is the repo's pattern and the cheapest to write, and the most expensive to flip: a store release per platform, with iOS waiting on a human. A withdrawal decided today reaches the field fastest through B or E; a withdrawal that must also reach installs of v0.20.0 and earlier cannot use A at all, since those builds carry no update client.
