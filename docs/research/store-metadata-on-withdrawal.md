# Store metadata when a listed feature is withdrawn

Research for [#2451](https://github.com/Selftend/selftend/issues/2451) (child of map [#2445](https://github.com/Selftend/selftend/issues/2445)). Every policy claim carries its official URL and the date it was read, **2026-09-15**. Repo claims are against `origin/dev` at `1c97653d` (2026-09-15). Anything not read from a primary source is marked **assumption**.

The question: once the app stops showing a module (CBT, ACT or DBT) on its production surfaces, what do Google Play and Apple require of the two listings, in what order, does a binary have to ship with it, how long does review take — and what has to be edited on the repo side so the store-copy gates stay green.

## Google Play

### What the policy says

- **Metadata policy** — _"We don't allow apps with misleading, improperly formatted, non-descriptive, irrelevant, excessive, or inappropriate metadata, including but not limited to the app's description, developer name, title, icon, screenshots, and promotional images."_ ([Metadata](https://support.google.com/googleplay/android-developer/answer/9898842), checked 2026-09-15.)
- **Deceptive Behaviour → Misleading Claims** — _"We don't allow apps that contain false or misleading information or claims, including in the description, title, icon, and screenshots."_ Listed example of a violation: _"Apps that misrepresent or do not accurately and clearly describe their functionality."_ ([Deceptive Behaviour](https://support.google.com/googleplay/android-developer/answer/9888077), checked 2026-09-15.)
- **Preview assets** — _"Screenshots must demonstrate the actual in-app or in-game experience, focusing on the core features and content."_ ([Add preview assets to showcase your app](https://support.google.com/googleplay/android-developer/answer/9866151), checked 2026-09-15.)

So yes: a description that lists CBT tools and ACT tools, a feature graphic whose lead mockup is the CBT module, and a screenshot of `/modules/cbt` all become _"misrepresent … their functionality"_ the day those screens are hidden from the production build. This is not a matter of taste; it is the clause Google removes listings under, and the repo already treats the questionnaire half of the same rule that way (`store/play-listing.md:95`).

### How a listing change is reviewed, and whether a release must ride with it

- Store listing changes are their own change type. Google's list of what Publishing overview holds for review runs: _"Full and staged roll-outs of your releases …, Launching and updating pre-registration, Store listing changes, including changes made to custom store listings and live store listing experiments, App content changes, Changes to your app category …"_ — releases and store listing changes are separate rows. ([Control when app changes are reviewed and published](https://support.google.com/googleplay/android-developer/answer/9859654), checked 2026-09-15.)
- **No binary is needed for a listing edit.** Google's page does not say so in one sentence — it is inferred from the list above plus the repo's own record: submissions 95–98 on 2026-09-06 were text-only and graphic-only listing changes with no release attached, and every one reached `Published` (`store/play-listing.md:5-10`, `:124`). **Assumption, weakly held:** a listing-only submission has never been refused for lacking a release in this project's history and nothing in the policy pages asks for one.
- **Review time** — _"All app changes need to be processed before they can be published. Processing can take a few hours or up to seven days (or longer in exceptional cases)."_ (same page, checked 2026-09-15). Observed here: submission 97 went from sent to `Published` in about 29 minutes and 95/96 cleared the same afternoon (`store/play-listing.md:12`). Plan on hours, check _Publishing overview → Submission activity_, and do not sit on a fix because the ceiling says seven days.
- Managed publishing is **off** for Selftend (`store/play-listing.md:135`), so an approved change goes live as soon as Google clears it — there is no second "publish" step to remember.

### The ordering problem Play creates, and the answer

A native store build carries whatever the app was built with; a listing edit is instant once cleared. The two do not land at the same moment, so one of these two windows exists:

1. **Listing edited first, release later** — for up to a few days the listing under-describes the app (says nothing about CBT while the installed app still shows it). No policy names that as a violation: the Metadata and Deceptive Behaviour pages forbid claiming what the app does _not_ do, not omitting what it does.
2. **Release first, listing later** — the listing over-describes: it names screens the app no longer has. That is the _"misrepresent … functionality"_ shape.

So the order that is never in breach is **listing first, or the same day as the release goes to production**, never after. Concretely for Play, in one Console visit so it costs one review (`store/play-listing.md:151`):

1. Full description: delete the ACT bullet (`:57`) and/or the CBT bullet (`:56`); if CBT leaves, rewrite ¶1 (`:51`) — that is the frame sentence, which is a positioning decision the map already flags as a third reposition, not a copy edit.
2. Feature graphic: replace `screen-cbt-home.png` in `docs/launch/play-listing/` with a tool capture, re-word the sentence at `feature-graphic.html:130` if CBT leaves the frame, re-screenshot the `.banner` at 1024×500 and upload (recipe at `store/play-listing.md:126-135`; the mockups are inside the graphic, so this is one asset, not three).
3. Screenshots: remove the `/modules/cbt` and/or `/modules/act` captures from all three slots (phone, 7", 10") and, if the count drops below what the layout needs, add tool captures — Play accepts 9:16 only, so the iOS files cannot be reused.
4. _Go to overview → Send changes for review_, having checked the change list names exactly the items above.

Nothing else on the listing moves: the "Meditation … ten-stage programme" bullet is a tool, "Private by design", the 18+ line and the "Important:" paragraph are unaffected.

## Apple App Store

### What the guidelines say

- **2.3 Accurate Metadata** — _"Customers should know what they're getting when they download or buy your app, so make sure all your app metadata, including privacy information, your app description, screenshots, and previews accurately reflect the app's core experience and remember to keep them up-to-date with new versions."_
- **2.3.1(a)** — _"marketing your app in a misleading way, such as by promoting content or services that it does not actually offer … whether within or outside of the App Store, is grounds for removal of your app from the App Store."_
- **2.3.3** — _"Screenshots should show the app in use, and not merely the title art, login page, or splash screen."_

([App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), checked 2026-09-15.) The phrase _"keep them up-to-date with new versions"_ is the whole answer to "must it change in the same version": Apple expects the metadata attached to the version that removes a feature to already not describe it.

### Which fields can change without a new version

| Field                          | Without a new version?                                                                                                                                                                                                                                                                                                                                                                                 | Source (checked 2026-09-15)                                                                                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Promotional text (`promoText`) | **Yes.** _"You can update promotional text at any time without having to submit a new version of your app."_                                                                                                                                                                                                                                                                                           | [Creating your product page](https://developer.apple.com/app-store/product-page/)                                                                                                      |
| Description                    | **No.** _"You can update your app's description when you submit a new version of your app."_                                                                                                                                                                                                                                                                                                           | same page                                                                                                                                                                              |
| Subtitle                       | **No** (and nothing to change — it is the method-free short form). _"You can update your subtitle when submitting a new version of your app."_                                                                                                                                                                                                                                                         | same page                                                                                                                                                                              |
| Screenshots / app previews     | **No.** A live version is not an editable status — the statuses reference marks _Prepare for Submission_ editable and says of _Waiting for Review_: _"you can't upload or edit screenshots or app previews"_; _Ready for Distribution_ carries no editable mark. The repo confirmed it live on 2026-08-18: the live version's media is locked and a new version draft is where screenshots are staged. | [App and submission statuses](https://developer.apple.com/help/app-store-connect/reference/app-and-submission-statuses/); `docs/positioning.md:109` names the current first screenshot |
| Keywords                       | **No** — a version-locked field; and it cannot be read from outside App Store Connect (`store/README.md:15`), so whether it contains `CBT`/`ACT` is unknown until the owner opens the field.                                                                                                                                                                                                           | **assumption** on the lock — Apple's product page does not list keywords; treated like description                                                                                     |
| What's New                     | Required for every version update (footnote 1 of the version-information table).                                                                                                                                                                                                                                                                                                                       | [Required, localizable, and editable properties](https://developer.apple.com/help/app-store-connect/reference/app-information/required-localizable-and-editable-properties/)           |

**A new version means a new build.** _"Ensure that the current version status is Ready for Distribution to initiate a new version"_; the metadata is copied forward; then _"Upload your new build to App Store Connect … add it to your latest version, then submit your app to App Review."_ ([Create a new version](https://developer.apple.com/help/app-store-connect/update-your-app/create-a-new-version), checked 2026-09-15.) The only things Apple reviews without an app version are in-app events, custom product pages and product page optimization tests ([Overview of submitting for review](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/overview-of-submitting-for-review), checked 2026-09-15). There is no metadata-only submission for description or screenshots.

**Review time** — _"On average, 90% of submissions are reviewed in less than 24 hours."_ ([App Review](https://developer.apple.com/distribute/app-review/), checked 2026-09-15.) Promotional text goes live on save; **assumption:** Apple's page says it needs no new version and says nothing about a review, and this project has not timed one.

### So, for Apple

1. **The day the withdrawal build is cut**, on the _live_ version: edit Promotional Text to drop _"CBT thought records"_ (only if CBT is withdrawn; ACT/DBT do not appear in it). Instant, no review, no binary.
2. **On the withdrawal version's draft** (created off the Ready-for-Distribution version, so it inherits the copy): rewrite the description wherever it names the withdrawn module (the owner has to read the full field first — the repo never captured it); open Keywords and remove the module's terms if present; in Media Manager replace the `02-cbt` / `03-act` screenshots in both the 6.9" and 13" slots, uploading one file at a time; write What's New; attach the build; submit. One review, ~24 h on Apple's average.
3. Because the metadata rides with the binary, **Apple never has a window where the listing lags the app** — provided step 2 is done on the same version and not left for "the next one".

1. Owner sets Promotional Text in App Store Connect on the live version (the withdrawal wording, or the current 168-character text if the field is simply blank).
2. Same day, a PR sets `store/apple-info.json:3` to the exact string saved — read back from the form, not retyped. Live first, file second, same day.
