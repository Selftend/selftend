# Research: Discord webhook delivery from the send-feedback Edge Function

**Date:** 2026-08-27 · **Ticket:** [#1483](https://github.com/Selftend/selftend/issues/1483) (part of #1481)

Facts a spec needs for posting each feedback submission to a Discord webhook from
`supabase/functions/send-feedback`, alongside the existing SES email path.

## 0. What the function does today (repo ground truth)

- `supabase/functions/send-feedback/index.ts` — auth via `supabase.auth.getUser()` (401 otherwise), 16 KB body cap (413), JSON parse (400), `validateFeedbackInput` (400), per-user rate limit via `record_feedback_submission` RPC (429), then an **awaited, inline** `sendEmail(...)` SES call; only after SES returns 2xx does the client get `{ success: true }`. Any throw (SES non-2xx included) lands in the outer catch → generic 500 (`index.ts:108-134`).
- Validation caps (`supabase/functions/_shared/feedback.ts:11,26-33`): category 1–40 chars (control chars stripped), message 10–1000 trimmed chars.
- `sendEmail` (`supabase/functions/_shared/ses.ts`) throws on any non-2xx SES response; nothing in `_shared/` knows about Discord yet.
- Client caller: `app/(app)/support.tsx:50-58` — `functions.invoke("send-feedback")`; any error shows a generic `feedback.submitError` toast. So the function's latency is user-facing spinner time.

## 1. Discord webhook contract

Sources (official; `discord.com/developers/docs/...` now 301s to `docs.discord.com`): [Webhook resource / Execute Webhook](https://docs.discord.com/developers/resources/webhook#execute-webhook), [Rate limits](https://docs.discord.com/developers/topics/rate-limits), [Embed limits](https://docs.discord.com/developers/resources/message#embed-object-embed-limits), [Opcodes & status codes](https://docs.discord.com/developers/topics/opcodes-and-status-codes), [API reference](https://docs.discord.com/developers/reference).

- **Endpoint & payload:** `POST /webhooks/{webhook.id}/{webhook.token}` with `Content-Type: application/json`. At least one of `content`, `embeds`, `components`, `file`, `poll` is required (else 400, JSON code 50006 "Cannot send an empty message"). Useful optional fields: `username`, `avatar_url` (per-message overrides), `allowed_mentions`, `embeds`. No auth header — the token in the URL is the credential.
- **Length limits vs our caps:** `content` allows **2000 characters**; our message is ≤1000 trimmed chars + category ≤40 — even with a small prefix ("[category] …") a plain-`content` post fits comfortably. If embeds are preferred: description ≤4096, title ≤256, ≤10 embeds, 6000 combined chars across all embeds. Violations → 400 Bad Request. (Note: user text should go through `allowed_mentions: { parse: [] }` or an embed to avoid `@everyone`/role pings from feedback content.)
- **Rate limits:** per-route buckets are keyed per webhook (`webhook_id + webhook_token` is an explicit top-level resource). **The docs publish no per-webhook number** — the widely quoted "5/2 s per webhook" and "30 msgs/min per channel" appear nowhere in the official docs; actual quota is discoverable only from `X-RateLimit-Limit/Remaining/Reset(-After)/Bucket/Scope` headers. Unauthenticated requests (webhooks) fall under a per-IP global limit, not the bot's 50 req/s. A 429 body carries `retry_after` (float seconds) and `global`; the response also has `Retry-After`. Our own `record_feedback_submission` per-user limit means one feedback ≈ one webhook POST, so 429s are unlikely in practice.
- **Success / error semantics:** default response is **204 No Content**; `?wait=true` returns 200 + the created message object (without `wait=true`, "a message that is not saved does not return an error"). Errors: 400 `{code, message, errors}` (e.g. 50035 invalid form body); 401 code 50027 "Invalid webhook token"; **404 code 10015 "Unknown webhook" for a deleted webhook — stop using it: repeated 404 retries trigger a temporary IP restriction** (invalid-request limit: 10k invalid requests / 10 min → Cloudflare ban). An outage looks like 502/5xx ("wait a bit and retry") or a connection timeout; no client-timeout guidance is documented.
- **URL secrecy:** the webhook `token` is "the secure token"; anyone with the URL can post AND (via the `.../with-token` endpoints, which "do not require authentication") modify or delete the webhook. The developer docs document **no token-regeneration API** — the documented recourse for a leaked URL is deleting the webhook (then 404/10015) and creating a new one. So the URL must be treated as a full secret (Edge Function secret store, never in the repo or client).

## 2. Fire-and-forget from a Supabase Edge Function

Sources: [Background Tasks](https://supabase.com/docs/guides/functions/background-tasks), [Limits](https://supabase.com/docs/guides/functions/limits), [shutdown reasons](https://supabase.com/docs/guides/troubleshooting/edge-function-shutdown-reasons-explained), [worker timeouts](https://supabase.com/docs/guides/troubleshooting/edge-functions-worker-timeouts-and-websocket-drops).

- **`EdgeRuntime.waitUntil(promise)`** marks background work: "The Function instance continues to run until the promise provided to `waitUntil` completes," letting you "respond to users while processing continues" (Background Tasks page). This is the right primitive for posting to Discord without adding its round-trip to the user-visible response.
- **A bare floating promise is NOT safe.** After the response returns, a worker with "no remaining async work" is retired (`EarlyDrop`, the most common shutdown reason — shutdown-reasons page); "EdgeRuntime.waitUntil() prevents early retirement" (worker-timeouts page). So the choice is: `await`-and-catch before returning (safe but adds Discord latency to the SES path's response), or `waitUntil` (no added latency). Never an un-tracked `fetch(...)`.
- **Guarantees are bounded, not absolute.** Background work runs only until the worker's wall-clock / CPU / memory limits: wall clock 150 s Free / 400 s paid, CPU 2 s, memory 256 MB (Limits page). "While you can't always rely on cleanup code running, implement it anyway" (shutdown-reasons page) — i.e. best-effort within limits; a `beforeunload` listener can log the shutdown reason. For a single ~1 KB Discord POST this budget is enormous; the realistic loss case is a rare instance shutdown, acceptable for a non-critical mirror of an email that already went out.
- **Wrap the background task in its own try/catch** (and optionally an `unhandledrejection` listener), per the Background Tasks page — an uncaught rejection inside `waitUntil` must not be able to affect anything. Note the current function's outer try/catch (`index.ts:126-134`) would NOT catch a rejection inside a `waitUntil` promise; the catch has to live inside the background task itself.
- **Local dev caveat:** with the CLI, instances terminate right after a request completes, so `waitUntil` work won't finish locally unless `supabase/config.toml` sets `[edge_runtime] policy = "per_worker"` (Background Tasks page). This repo's `config.toml` has no `[edge_runtime]` section today, so local testing of the fire-and-forget path needs that addition (or temporarily awaiting).

## 3. Secret handling in this repo (staging vs prod)

- **CI deploys are code-only.** Both deploy jobs run bare `supabase functions deploy` after `supabase link --project-ref "$..._PROJECT_ID"`, with the explicit comment "Code only; function runtime secrets stay managed in the Supabase project (decision #17)" — `.github/workflows/release.yml:150-154` (production environment, `PRODUCTION_PROJECT_ID`) and `.github/workflows/staging.yml:108-112` (staging environment, `STAGING_PROJECT_ID`). Issue [#17](https://github.com/Selftend/selftend/issues/17) ("Decide: production DB migration automation") is where that split was decided.
- **Per-environment = per-project.** Staging and production are separate Supabase projects (separate `*_PROJECT_ID` GitHub Environment secrets), so each has its own independent Edge Function secret store. A new `DISCORD_WEBHOOK_URL` (or similar) must be set once per project — dashboard or `supabase secrets set` — and CI never touches it.
- **Existing runtime secrets precedent:** the SES credentials (`SES_ACCESS_KEY_ID`, `SES_SECRET_ACCESS_KEY`, `SES_REGION`, `SES_FROM_EMAIL`) plus `SUPPORT_EMAIL` are read via `Deno.env.get` (`index.ts:13-17,103-112`) and documented as function env in `docs/launch/smtp-deliverability-checklist.md:20-24`. `SUPABASE_URL` / `SUPABASE_ANON_KEY` come from the platform's built-in env.
- **Runbook caveat:** `docs/operations-runbook.md:29` says the Vault key can be created "via the CLI `supabase secrets set`" — that is imprecise: `supabase secrets set` manages **Edge Function** secrets, while `app_field_encryption_key` is a **Vault** secret (SQL/dashboard Vault UI). Don't copy that sentence into the webhook spec.
- **Official mechanics** ([Secrets docs](https://supabase.com/docs/guides/functions/secrets), [CLI ref](https://supabase.com/docs/reference/cli/supabase-secrets-set)): `supabase secrets set NAME=VALUE` targets the linked project (or `--project-ref`); functions read via `Deno.env.get`. **"You don't need to re-deploy after setting your secrets. They're available immediately in your functions."** — so secret rotation and code deploys are fully independent, and a deploy picks up whatever the project's secret store currently holds. Limits: 100 secrets/project, 48 KiB each.
- **Local dev:** there is no `supabase/functions/.env` in the repo today; the Supabase CLI auto-loads `supabase/functions/.env` when serving locally (and it must never be committed — official docs). Local runs currently supply function env ad hoc.

## Bottom line for the spec

- One JSON POST with plain `content` (≤2000 chars) fits our ≤1040-char payload; set `allowed_mentions: { parse: [] }`; treat 204 as success; never retry a 404.
- Deliver via `EdgeRuntime.waitUntil` with the try/catch **inside** the background task — the SES path's latency and status stay untouched, at the cost of best-effort delivery (fine for a mirror of an email that already sent). A bare floating fetch is not safe; awaiting adds Discord's round-trip to the user's spinner.
- `DISCORD_WEBHOOK_URL` is a per-project Edge Function secret (staging + prod set separately, dashboard or `supabase secrets set`); CI deploys never touch secrets (decision #17) and no redeploy is needed after setting/rotating it. The webhook URL is a full credential (post + modify + delete); adding it is a new external dependency + credential → control-tower per the architecture rule.
- Do **not** route the webhook URL through `requiredEnv` (`index.ts:13-17` throws → whole function 500s): an absent secret should mean "skip Discord", keeping the feature optional per environment.

## Premise check (ticket vs code)

- ✓ 1000-char feedback cap — confirmed (`feedback.ts:31`), plus a 40-char category; both fit far under Discord's `content` limit.
- ✓ CI runs `supabase functions deploy` in both workflows — confirmed, and it is deliberately secret-free.
- ✗ "per-webhook rate limits" as a documentable number — the official docs define per-webhook _buckets_ but publish **no** per-webhook rate; the famous "5/2 s" figure is folklore. The contract is: obey the `X-RateLimit-*` headers / `retry_after`.
- ✗ (near-miss) "docs/operations-runbook.md etc." as the secrets doc — the runbook's only `supabase secrets` mention is the imprecise Vault line above; the real prior art for function secrets is the workflow comments (decision #17) and `docs/launch/smtp-deliverability-checklist.md`.
